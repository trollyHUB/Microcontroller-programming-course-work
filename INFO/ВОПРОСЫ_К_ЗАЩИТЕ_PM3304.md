# БЛОК 1 — ESP32: АППАРАТНАЯ ПЛАТФОРМА

**Q: Какой именно контроллер используете? Назовите точную модель.**
> ESP32 DevKit V1 — 30-пиновая версия. Чип: **ESP32-D0WDQ6**, двойное ядро Xtensa LX6, 240 МГц. Не путать с 38-пиновой DevKit V4 — у нас 30 pin. На плате: USB-UART мост CP2102, LDO-регулятор 3.3V/600 мА, кнопки EN (reset) и BOOT (флешинг).

---

**Q: Почему ESP32, а не Arduino Uno/Nano?**
> Три конкретные причины:
> 1. **RAM**: Uno — 2 КБ SRAM. Один JSON-пакет для HTTP POST занимает ~300 байт, плюс стек WiFi ~40 КБ, плюс буферы датчиков. На Uno физически невозможно. ESP32 — 520 КБ SRAM, свободно ~312 КБ.
> 2. **Wi-Fi**: Uno требует внешний ESP8266/W5100. ESP32 — Wi-Fi 802.11 b/g/n встроен в чип.
> 3. **GPIO**: Uno — 14 цифровых + 6 аналоговых. ESP32 — 25 программируемых GPIO, 18 каналов АЦП, 16 PWM, 3 UART, 2 I2C, 4 SPI.

---

**Q: У ESP32 два ядра. Вы оба используете?**
> В Arduino Framework оба ядра активны, но Arduino loop() работает на ядре 1. Ядро 0 занято Wi-Fi/BT стеком (Espressif SDK). Мы явно не создаём задачи FreeRTOS — используем кооперативную многозадачность через millis(). Это осознанное решение: для данной задачи нет смысла усложнять код RTOS при одном потоке данных.

---

**Q: Почему не STM32?**
> STM32 мощнее по числодробилке, но: нет встроенного Wi-Fi (нужен внешний модуль + SPI), требует FreeRTOS для нормальной многозадачности, toolchain сложнее (HAL/LL vs Arduino). Для IoT-прототипа с Wi-Fi ESP32 — очевидный выбор.

---

**Q: Что такое Input-only пины GPIO34, 35, 36, 39?**
> Эти пины не имеют выходных драйверов — только АЦП вход. Нельзя настроить как OUTPUT. Нет внутреннего pull-up/pull-down. Мы используем GPIO36 (VP) → MQ-135 и GPIO39 (VN) → KY-037 — корректно: только аналоговое чтение.

---

**Q: Почему ADC1, а не ADC2?**
> ADC2 (GPIO0, 2, 4, 12–15, 25–27) **конфликтует с Wi-Fi радиомодулем** — при активном Wi-Fi ADC2 возвращает некорректные значения или зависает. ADC1 (GPIO32–39) работает независимо от Wi-Fi. Поэтому KY-037 → GPIO39, MQ-135 → GPIO36 — оба на ADC1.

---

**Q: Какова точность АЦП ESP32?**
> 12-бит: диапазон 0–4095 при 0–3.3V (теоретически). На практике АЦП ESP32 нелинеен: погрешность до 10–15% особенно на краях (0–100 мВ и 3100–3300 мВ). Для шума (KY-037) это допустимо — нам нужен относительный уровень, не абсолютные дБ. Для критичных измерений нужна внешняя опорная калибровка или внешний АЦП (ADS1115).

---

**Q: Объясните пины питания: VIN, 3V3, GND?**
> - **VIN (пин 30)**: 5V напрямую от USB через диод защиты. Подаётся на устройства 5V: ZM106-VOC, PIR HC-SR501, LCD 1602.
> - **3V3 (пин 1)**: выход встроенного LDO-регулятора. Подаётся на: BME280, BH1750, DHT11, KY-037. Максимальный ток LDO — 600 мА (у некоторых версий 300 мА).
> - **GND (пины 2, 29)**: общая земля всей схемы. Все GND объединены.

---

**Q: Какое максимальное потребление тока у GPIO-пинов ESP32?**
> Максимально 40 мА на один GPIO (рекомендуется ≤12 мА). Для RGB LED используем резисторы 220 Ом: при 3.3V ток = (3.3 - 2.0) / 220 = ~6 мА на канал — в норме. Без резисторов GPIO сгорит.

---

**Q: Почему RGB LED с общим катодом, а не с общим анодом?**
> С общим катодом: катод → GND, каждый анод управляется GPIO через резистор. GPIO HIGH = LED горит. Логика прямая. С общим анодом: анод → 3V3, GPIO HIGH = LED НЕ горит (инвертированная логика). Для простоты кода — общий катод предпочтительнее.

---

**Q: Расчёт резистора для LED?**
> Закон Ома: R = (Vcc - Vled) / I. Для красного LED: Vled ≈ 2.0V, I = 10 мА. R = (3.3 - 2.0) / 0.01 = 130 Ом. Взяли 220 Ом — с запасом, ток ~6 мА, LED светит достаточно ярко при меньшем нагреве.

# БЛОК 2 — ДАТЧИКИ (самый строгий блок)

**Q: Почему BME280, а не BME680 или SHT31?**
> - **BME680** добавляет датчик газа (VOC), но стоит в 3× дороже (~7500 ₸), и у нас уже есть ZM106 для качества воздуха — дублирование.
> - **SHT31**: только T/H, нет давления. BME280 даёт T+H+P на одном чипе.
> - BME280 по Bosch — промышленный стандарт: ±1°C, ±3% RH, ±1 hPa. Оптимально для проекта.

---

**Q: BME280 может давать завышенную температуру — почему?**
> ESP32 при активном Wi-Fi (240 МГц) рассеивает ~0.5–1 Вт тепла. Если BME280 расположен вплотную к ESP32, тепловое излучение платы завышает показания на 1–3°C. Решение: разнести модули на 5–10 см или использовать выносной датчик на шлейфе. В прототипе это известное ограничение.

---

**Q: Как подключён BME280? Адрес I2C?**
> I2C: SDA=GPIO21, SCL=GPIO22. Адрес **0x76** (когда SDO пин подключён к GND). Если SDO → VCC — адрес 0x77 (позволяет поставить два BME280 на одну шину). Питание 3.3V (VCC). Подтягивающие резисторы 4.7 кОм встроены в модуль.

---

**Q: Что такое ZM106-VOC? Это настоящий CO₂ датчик?**
> **Нет.** ZM106 — электрохимический датчик **суммарных летучих органических соединений (VOC)**. Реагирует на CO₂, этанол, аммиак, бензол и другие газы одновременно. Он коррелирует с CO₂ в типичных офисных условиях (дыхание людей выдыхает и CO₂, и VOC вместе), но не является NDIR CO₂-сенсором. Истинные CO₂: MH-Z19B (~3000 ₸), SCD41 (~8000 ₸). В перспективах — замена на SCD41.

---

**Q: Объясните протокол ZM106 детально.**
> UART: RX=GPIO16, TX=GPIO17, 9600 baud, 8N1, без контроля чётности.
>
> **Запрос** (ESP32 → датчик, 9 байт):
> ```
> FF 01 86 00 00 00 00 00 79
> │  │  │                  └─ CRC
> │  │  └──────────────────── Команда: Read PPM
> │  └─────────────────────── Адрес датчика: 01
> └────────────────────────── Заголовок: FF
> ```
>
> **Ответ** (датчик → ESP32, 9 байт):
> ```
> FF 86 HIGH LOW 00 00 00 00 CRC
> ```
> Концентрация (ppm) = `(HIGH << 8) | LOW`
>
> **Расчёт CRC**: `CRC = (~(byte[1] + byte[2] + ... + byte[7])) + 1` (дополнение до 2)
>
> Пример: HIGH=0x02, LOW=0x8A → ppm = 0x028A = 650 ppm
>
> Таймаут ожидания ответа: 500 мс. Если нет ответа → `zm106OK = false`, данные не отправляются (null в JSON).

---

**Q: Почему уровни логики ZM106 и ESP32 разные? Как решили?**
> ZM106 работает на 5V логике (TX датчика = 5V HIGH). ESP32 GPIO: максимум 3.6V на входе. На RX-линию ESP32 (GPIO16) 5V-сигнал теоретически может повредить GPIO. На практике большинство ESP32 GPIO толерантны к 5V (datasheet не гарантирует, но на практике работает). Правильное решение: делитель напряжения (R1=10кОм, R2=20кОм) или уровень-конвертер. В учебном прототипе — напрямую, работает стабильно.

---

**Q: Почему PIR HC-SR501, а не ультразвуковой SR04 или камера?**
> - **SR04** (ультразвук): измеряет расстояние ~2 мс цикл, требует постоянного опроса, потребляет 15 мА. Не может различить «человек есть» от «стул придвинут к столу».
> - **Камера**: нужен ESP32-CAM (другая плата), требует ML для детекции, дорого и сложно.
> - **PIR**: обнаруживает тепловое излучение движущегося тела. Пассивный — не излучает ничего. 65 мкА в ожидании. Дальность 3–7 м — покрывает рабочее место. Идеален для задачи «есть ли человек».

---

**Q: PIR питается от 5V, но выдаёт 3.3V логику — как?**
> HC-SR501: питание 4.5–12V (у нас 5V от VIN). Выходной сигнал OUT — HIGH **3.3V** (внутренний делитель). Прямо совместим с ESP32 GPIO без преобразования уровней.

---

**Q: Почему BH1750, а не фоторезистор (LDR)?**
> Фоторезистор: аналоговый сигнал → АЦП → нужна калибровочная кривая для конкретного источника света → результат в ADC-единицах, не в люксах. Нелинейная характеристика. BH1750: цифровой I2C, встроенный АЦП 16-бит, результат напрямую в **люксах** (SI единица), диапазон 1–65535 лк, не занимает пины АЦП.

---

**Q: Что за KY-037? Как переводит ADC в децибелы?**
> KY-037 — электретный конденсаторный микрофон с усилителем. Два выхода:
> - AO (аналоговый): пропорционален амплитуде звука → GPIO39 ADC1, 12-бит (0–4095)
> - DO (цифровой): HIGH/LOW при превышении настроенного порога (потенциометром) — не используется
>
> Перевод: `dB = 30 + (adc_value / 4095.0) × 60` → диапазон 30–90 дБ.
> Это линейная аппроксимация, не калибровка. Достаточно для относительного сравнения уровней.

---

**Q: DHT11 тоже подключён. Зачем, если есть BME280?**
> DHT11 — **резервный датчик** для cross-check температуры и влажности. BME280 — основной. Если показания расходятся > 3°C — сигнал о неисправности BME280 или его перегреве от платы. В прошивке DHT11 читается параллельно, результат выводится отдельно на одном из экранов LCD.

---

**Q: Почему INPUT_PULLUP для кнопок, а не внешний резистор?**
> ESP32 GPIO имеет встроенные pull-up резисторы ~45 кОм. INPUT_PULLUP их подключает программно — экономим 2 внешних резистора и провода. Работает надёжно: в покое GPIO=HIGH, нажатие → GND → LOW. Без pull-up GPIO «висит в воздухе» — случайные HIGH/LOW от наводок (floating input).

---

**Q: LCD 1602 — почему I2C, а не параллельный 4-бит?**
> Параллельный режим LCD требует 6 пинов GPIO (RS, EN, D4-D7). I2C-модуль PCF8574 позволяет управлять LCD по 2 проводам (SDA/SCL), уже занятым под BME280 и BH1750. Экономия 4 GPIO. Адрес 0x27 (стандарт для PCF8574).

---

# БЛОК 3 — ПРЕРЫВАНИЯ (главный вопрос дисциплины)

**Q: Объясните механизм прерываний ESP32 от GPIO.**
> ESP32 поддерживает GPIO-прерывания по уровню и фронту сигнала. При регистрации через `attachInterrupt()` аппаратный контроллер прерываний (INTC) отслеживает изменение на указанном GPIO без участия программного кода. При событии — текущая инструкция CPU прерывается, PC сохраняется в стек, управление передаётся ISR. После ISR — восстановление контекста, продолжение прерванного кода.

---

**Q: Зачем вам вообще прерывания? Polling ведь проще.**
> Polling работал бы — но с конкретными техническими потерями:
>
> **Проблема 1 — PIR:** движение длится 0.3–0.5 с. В loop() между опросами может пройти: HTTP POST (42 мс сеть) + DHT чтение (50 мс) + ZM106 UART (500 мс таймаут) = суммарно до 600 мс. Движение физически произошло и закончилось между двумя вызовами `digitalRead(PIR)` — **пропущено**.
>
> **Проблема 2 — кнопки:** нажатие 50–100 мс. Если loop() занят ZM106 (500 мс таймаут) — кнопка нажата и отпущена, polling её не поймает.
>
> **Вывод:** ISR гарантирует регистрацию события в момент его возникновения, независимо от того, чем занят loop(). Это не академизм — это конкретное требование надёжности.

---

**Q: Покажите код ISR и объясните каждую строку.**
> ```cpp
> // volatile — запрет кэширования в CPU-регистре
> // bool — минимальный тип, атомарная запись на Xtensa LX6
> volatile bool isrBtnMode = false;
> volatile bool isrBtnOK   = false;
> volatile bool isrPIR     = false;
>
> // IRAM_ATTR — размещает функцию в Internal RAM (не Flash)
> // Без IRAM_ATTR ISR из Flash может вызвать crash
> // при операциях с Flash на другом ядре
> void IRAM_ATTR onBtnMode() { isrBtnMode = true; }
> void IRAM_ATTR onBtnOK()   { isrBtnOK   = true; }
> void IRAM_ATTR onPIR()     { isrPIR     = true; }
> ```
>
> В setup():
> ```cpp
> // FALLING — кнопки с INPUT_PULLUP: нажатие = HIGH→LOW
> attachInterrupt(digitalPinToInterrupt(PIN_BTN_MODE), onBtnMode, FALLING);
> attachInterrupt(digitalPinToInterrupt(PIN_BTN_OK),   onBtnOK,   FALLING);
> // RISING — PIR: движение = LOW→HIGH
> attachInterrupt(digitalPinToInterrupt(PIN_PIR),      onPIR,     RISING);
> ```

---

**Q: Что такое IRAM_ATTR и почему без него ISR может упасть?**
> ESP32 хранит код в Flash-памяти (SPI Flash, внешняя). Доступ к Flash кэшируется. Если ISR находится в Flash, а в момент прерывания другой поток (например, Wi-Fi stack на ядре 0) выполняет запись во Flash или инвалидирует кэш — ISR не сможет загрузить свой код → **Guru Meditation Error (Cache disabled but cached memory region accessed)**. IRAM_ATTR размещает функцию в Internal RAM (160–192 КБ IRAM, скорость доступа 1–2 нс) — Flash-проблема исключена.

---

**Q: Почему volatile?**
> Компилятор C++ агрессивно оптимизирует: если он видит, что переменная не меняется в текущем контексте (loop не пишет в `isrBtnMode`) — может закэшировать её в CPU-регистре и читать из регистра, игнорируя RAM. ISR пишет в RAM — loop читает старое значение из регистра. `volatile` говорит компилятору: **каждый раз читай из RAM, не оптимизируй**. На многоядерном ESP32 это также предотвращает видимость изменений между ядрами (хотя для полной гарантии нужен ещё memory barrier — в данном случае не критично, т.к. ISR и loop на одном ядре).

---

**Q: Почему ISR только ставит флаг, а не делает всё сразу?**
> ISR прерывает выполнение любого кода — включая критические секции операционной системы. Внутри ISR строгие ограничения:
> - **Нельзя**: `delay()`, `Serial.print()`, `Wire.` (I2C), `http.POST()`, `malloc()`, любые blocking функции
> - **Нельзя**: вызывать функции, которые сами не помечены IRAM_ATTR
> - **Нельзя**: держать ISR дольше ~10 мкс (иначе watchdog сбросит процессор)
>
> Паттерн «флаг + обработка в loop()» — стандарт встраиваемых систем. ISR = сигнальщик (только флаг), loop = исполнитель (логика).

---

**Q: Что такое debounce и как реализован?**
> Механический контакт кнопки при нажатии вибрирует 5–20 мс — генерирует серию HIGH/LOW переходов. Каждый переход — новое срабатывание ISR. Без защиты одно нажатие → 10–50 вызовов ISR.
>
> Реализация (временна́я маска в loop):
> ```cpp
> void handleButtons() {
>     uint32_t now = millis();
>     if (isrBtnMode && (now - btnModeLast > DEBOUNCE_MS)) {
>         isrBtnMode = false;     // сброс флага
>         btnModeLast = now;       // запомнить время
>         // ... логика кнопки
>     }
> }
> ```
> `DEBOUNCE_MS = 200` мс — достаточно для любой механической кнопки (дребезг < 20 мс). За 200 мс все дребезги утихли, следующее легитимное нажатие можно зафиксировать.

---

**Q: Какие режимы прерываний существуют в ESP32?**
> | Константа | Срабатывание |
> |-----------|-------------|
> | `RISING` | LOW→HIGH (нарастающий фронт) |
> | `FALLING` | HIGH→LOW (спадающий фронт) |
> | `CHANGE` | любое изменение уровня |
> | `LOW` | пока уровень LOW (level triggered) |
> | `HIGH` | пока уровень HIGH (level triggered) |
>
> Level-triggered (`LOW`/`HIGH`) вызывает ISR непрерывно пока уровень сохраняется — нужно быть осторожным. В проекте: FALLING (кнопки), RISING (PIR).

---

**Q: Можно ли было использовать CHANGE для кнопок?**
> Технически да — ISR сработает и на нажатие (FALLING), и на отпускание (RISING). Но тогда нужно внутри ISR различать направление изменения через `digitalRead()` — это дополнительный код в ISR (нежелательно) и лишние срабатывания. FALLING — чище: только момент нажатия.

# БЛОК 4 — ИНТЕРФЕЙСЫ И ПРОТОКОЛЫ

**Q: Объясните I2C протокол на уровне сигналов.**
> I2C: 2 линии — **SDA** (данные) и **SCL** (тактирование). Оба провода подтянуты к VCC через резисторы (pull-up ~4.7 кОм). Линии в покое = HIGH.
>
> Транзакция (мастер = ESP32):
> 1. **START**: SDA HIGH→LOW при SCL=HIGH (специальное условие)
> 2. **Адрес** (7 бит) + бит R/W: мастер тактирует SCL, выдаёт биты на SDA
> 3. **ACK**: slave тянет SDA в LOW (подтверждение)
> 4. **Данные**: 8 бит + ACK, повторять
> 5. **STOP**: SDA LOW→HIGH при SCL=HIGH
>
> Скорость: 100 кбит/с (Standard), 400 кбит/с (Fast). В проекте — 100 кбит/с.

---

**Q: Три устройства на одной I2C-шине — как не конфликтуют?**
> I2C — адресная шина. Каждое устройство имеет уникальный 7-битный адрес (2⁷ = 128 возможных устройств). Мастер начинает каждую транзакцию с адреса нужного устройства. Остальные игнорируют. В проекте: BME280 = 0x76, BH1750 = 0x23, LCD (PCF8574) = 0x27 — три разных адреса, конфликтов нет.

---

**Q: UART — объясните Serial2 для ZM106.**
> UART — асинхронный, без тактирующего сигнала. Стороны заранее договариваются о скорости (baud rate). В ESP32 три UART-контроллера:
> - UART0: GPIO1(TX)/GPIO3(RX) — зарезервирован для Serial Monitor (115200 baud)
> - UART2: GPIO17(TX)/GPIO16(RX) — используем для ZM106 (9600 baud, 8N1)
>
> 8N1: 8 бит данных, No parity, 1 stop bit. Стандарт для большинства UART-устройств.

---

**Q: Что такое SPI? Почему не используете для датчиков?**
> SPI — синхронный 4-проводной протокол: MOSI, MISO, SCK, CS. Для каждого устройства нужен отдельный CS-пин. У нас 3 I2C устройства на 2 проводах против 3 SPI устройств на 3+3=6 проводах. I2C экономит GPIO. Для SD-карты планировалось SPI: CS=GPIO5, MOSI=GPIO23, MISO=GPIO19, SCK=GPIO18.

---

**Q: Почему HTTP, а не MQTT для отправки данных?**
> HTTP/REST — проще для прототипа: библиотека HTTPClient встроена, сервер — стандартный FastAPI без брокера. MQTT требует брокер (Mosquitto, HiveMQ) — дополнительный компонент. Для production с сотнями устройств MQTT лучше (persistent connections, QoS, retain). Для учебного прототипа с одним устройством HTTP — оправданный выбор.

---

**Q: Что в JSON-пакете? Размер?**
> ```json
> {"temperature":23.5,"humidity":45.2,"pressure":1013.1,
>  "co2":650,"light":420.5,"noise":38.2,"motion":false,
>  "alert_level":0,"pomo_mode":0,"pomo_cycles":2}
> ```
> ~180 байт. С HTTP-заголовками (Content-Type, Host) — ~350 байт на запрос. ArduinoJson v7 формирует это без ручного sprintf.

---

**Q: Что происходит при потере Wi-Fi?**
> `checkWiFi()` в каждом loop(): если `WiFi.status() != WL_CONNECTED` → `WiFi.reconnect()` + `state.wifiConnected = false`. `postToServer()` проверяет флаг первой строкой: `if (!state.wifiConnected) return;`. Данные за время отключения **теряются** — это ограничение прототипа. Решение в перспективах: буфер на SD-карту.

---

**Q: Что такое WebSocket и зачем он в сервере?**
> WebSocket (RFC 6455): двунаправленный постоянный TCP-канал между браузером и сервером. HTTP — запрос/ответ (браузер инициирует). WebSocket — push (сервер инициирует). При получении POST `/api/data` от ESP32 сервер вызывает `await sio.emit('sensor_update', data)` — данные **мгновенно** поступают в браузер без опроса. Альтернатива — polling `GET /api/sensors` каждые N секунд — задержка + лишняя нагрузка.

# БЛОК 5 — ПРОГРАММНАЯ ЧАСТЬ

**Q: Почему millis() а не delay() в loop()?**
> `delay(10000)` блокирует процессор на 10 секунд — никакого кода не выполняется: ни кнопки, ни ISR-обработка, ни дисплей. `millis()` возвращает время с запуска (мс). Паттерн:
> ```cpp
> if (millis() - lastTime > INTERVAL) {
>     lastTime = millis();
>     // действие
> }
> ```
> loop() продолжает крутиться, проверяет флаги ISR, обновляет дисплей. Кооперативная многозадачность без RTOS.

---

**Q: Что такое ArduinoJson v7? Почему v7, а не v6?**
> ArduinoJson — библиотека сериализации JSON для MCU. v6: `StaticJsonDocument<512> doc` — нужно заранее указать размер буфера в байтах. v7: `JsonDocument doc` — динамическое выделение, автоматический размер. Меньше кода, нет риска переполнения буфера. v7 актуальная версия на 2026 год.

---

**Q: Как работает setup()/loop() архитектура?**
> `setup()` выполняется один раз при старте: инициализация Serial, Wire (I2C), GPIO, Wi-Fi, датчиков, ISR. `loop()` — бесконечный цикл. Arduino Framework вызывает `loop()` снова и снова. Среднее время одной итерации loop() в проекте: ~5–15 мс (без HTTP POST). С HTTP POST (10-секундный интервал): ~50–100 мс.

---

**Q: Зачем нужен Watchdog timer в ESP32?**
> ESP32 имеет Task Watchdog Timer (TWDT). Если loop() не возвращает управление SDK (или не вызывает `yield()`/`delay()`) в течение ~5 секунд — Watchdog сбрасывает CPU (Guru Meditation). Это защита от зависания. Поэтому важно: длинные операции делать через millis() или с yield(), а не через delay(). В нашем коде: UART-таймаут ZM106 = 500 мс — безопасно.

---

**Q: Почему FastAPI, а не Flask?**
> Flask: WSGI (синхронный). FastAPI: ASGI (асинхронный). Socket.IO требует ASGI для WebSocket. Flask + Socket.IO = дополнительный эмулятор async (eventlet/gevent) — хрупкая конструкция. FastAPI + python-socketio нативно async — чистая архитектура. Плюс FastAPI: автоматический Swagger UI на /docs, Pydantic-валидация, в 2× быстрее Flask.

---

# БЛОК 6 — НЕСТАНДАРТНЫЕ ВОПРОСЫ

**Q: Что такое COGfx Study (Harvard, 2015)?**
> Исследование Гарвардской школы общественного здравоохранения (Allen et al., 2016, опубликовано в Environmental Health Perspectives). Участники работали в офисах с разным уровнем CO₂ (550, 945, 1400 ppm). При 1000 ppm когнитивные показатели (decision-making, information usage) снижались на 15–50% по сравнению с 550 ppm. Это обоснование пороговых значений CO₂ в проекте.

---

**Q: Что такое техника Pomodoro?**
> Разработана Франческо Чирилло (конец 1980-х). Принцип: 25 минут работы (Pomodoro) → 5 минут отдыха → после 4 Pomodoro — длинный перерыв 15–30 минут. Название — от кухонного таймера в форме помидора (итал. pomodoro). В NEXIS: счётчик выполненных Pomodoro, логирование на сервер через POST /api/pomodoro, PIR-автопауза при отсутствии движения > 15 с.

---

**Q: Чем обоснован выбор именно 10 секунд для интервала POST?**
> Компромисс: параметры микроклимата изменяются медленно (CO₂ растёт ~10 ppm/мин в закрытом помещении с человеком). Интервал 10 с: 8640 записей/сутки → 60 КБ/сутки в SQLite — управляемо. Интервал 1 с дал бы 86400 записей → 600 КБ/сутки, но без значимой дополнительной информации. Интервал 60 с — слишком редко для оперативного алерта.

---

**Q: Как хранятся данные в браузере?**
> localStorage: без сервера хранятся `nexis-theme` (светлая/тёмная), `nexis-temp-unit` (°C/°F), `nexis-demo-interval` (мс), `nexis-pomo-cycles` (счётчик Pomodoro между сессиями). При полной выгрузке данных с сервера — кольцевой буфер `state.chartData` (до 200 точек в RAM браузера, не в localStorage).

---

**Q: Что такое CSV-экспорт с BOM? Зачем?**
> BOM (Byte Order Mark) — три байта `EF BB BF` в начале файла. Указывает Excel на кодировку UTF-8. Без BOM Excel на русской локали открывает UTF-8 файл как CP1251 → кракозябры в заголовках столбцов. Разделитель `;` (точка с запятой): в русской локали Excel по умолчанию ожидает `;`, а не `,` (которая — десятичный разделитель в русских числах).

---

**Q: Что такое демо-режим?**
> Режим работы дашборда без подключённого ESP32. JavaScript генерирует псевдореалистичные данные: температура 20–28°C с дрейфом, CO₂ 400–1200 ppm с циклическими нарастаниями, освещённость 100–600 лк. Данные идут в тот же `state.chartData` — все графики, аналитика, Pomodoro работают в полном объёме. Позволяет демонстрировать систему без железа.

---

**Q: Вы сказали — прошивка ~750 строк C++. Это много или мало?**
> Для Arduino-проекта с 7 датчиками, LCD, Wi-Fi, HTTP, UART, ISR, Pomodoro — компактно. Основные функции: `readSensors()`, `checkThresholds()`, `updateLED()`, `updateDisplay()`, `postToServer()`, `updatePomodoro()`, `handleButtons()`, `readPIR()`, `checkWiFi()`. Монолитный файл main.cpp — обычная практика для Arduino.

---

**Q: Каков расход Flash и RAM? Насколько близко к пределу?**
> После компиляции: **Flash 74.4%** (из 4 МБ), **RAM 14.7%** (из 520 КБ). Запас существенный. Основные потребители Flash: Wi-Fi stack (~500 КБ), SSL (~200 КБ если нужен HTTPS — у нас HTTP без TLS), библиотеки. RAM: Wi-Fi heap ~40 КБ, ArduinoJson буфер ~1 КБ, String объекты.

---

**Q: Почему не используете HTTPS для POST?**
> TLS требует ~50–100 КБ RAM для SSL-контекста и значительно увеличивает Flash. На ESP32 возможно, но: а) сервер — в локальной сети (HTTP по LAN безопасен от внешних атак), б) данные не конфиденциальные (температура и влажность), в) TLS добавляет латентность 200–500 мс на handshake. Для прототипа — избыточно.

---

**Q: Почему выбрали SQLite, а не просто CSV-файл на сервере?**
> CSV: нет индексов → выборка истории за 24 часа = чтение всего файла (O(n)). SQLite: индекс по timestamp → быстрый range-запрос O(log n). Транзакции: при одновременном POST от ESP32 и GET от браузера без SQLite — race condition и повреждение файла. SQLite гарантирует атомарность (ACID). CSV — никак.

# БЛОК 7 — SD-КАРТА (если спросят)

**Q: У вас есть SD-карта? Почему не реализована?**
> Модуль SD-карты присутствует в спецификации как расширение. Физически чип подключается по SPI: CS=GPIO5, MOSI=GPIO23, MISO=GPIO19, SCK=GPIO18 — эти пины свободны в текущей схеме. Библиотека: `SD.h` из Arduino ESP32. Не реализована в текущей версии — данные полностью передаются через Wi-Fi в реальном времени. SD-карта нужна как буфер при потере сети — это следующая итерация разработки.

---

**Q: Как бы выглядела реализация SD-карты?**
> ```cpp
> #include <SD.h>
> #define SD_CS 5
>
> // В setup():
> SD.begin(SD_CS);
>
> // При потере Wi-Fi вместо потери данных:
> void logToSD(SensorData& s) {
>     File f = SD.open("/log.csv", FILE_APPEND);
>     f.printf("%s,%.1f,%.1f,%.0f,%d\n",
>              timestamp, s.temperature, s.humidity,
>              s.pressure, s.co2);
>     f.close();
> }
> // При восстановлении Wi-Fi: читать CSV, POST каждой строки
> ```
